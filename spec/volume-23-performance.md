## 23.1 Compilation performance and the phase budget contract (defines design.md 31.1, bullets B31-1..B31-15)

The compiler is divided into exactly the 15 phases of design.md §31.1, in pipeline order. The **budget contract**: (B1) the total compile time of W1 must be ≤ 30 s at `-O0` and ≤ 120 s at `-O2` on the reference machine; (B2) the per-phase budget = the phase's share of the total, per the table below; (B3) any single source file must complete the full frontend (lexing through borrow check) in ≤ 5 s at `-O0`; (B4) the regression gate of §23.5 applies per phase. Exceeding a hard bound (B1, B3) fails CI; exceeding a phase budget (B2) is a tracked warning with a mandatory review record.

| Bullet | Phase | Share of total |
| --- | --- | --- |
| B31-1 | Lexing | 4% |
| B31-2 | Parsing | 8% |
| B31-3 | Name resolution | 7% |
| B31-4 | Type checking | 12% |
| B31-5 | Trait solving | 10% |
| B31-6 | Borrow checking | 8% |
| B31-7 | Effect inference | 4% |
| B31-8 | IR 1 construction | 6% |
| B31-9 | IR 1 optimization | 8% |
| B31-10 | IR 2 construction | 4% |
| B31-11 | IR 2 optimization | 8% |
| B31-12 | Machine lowering | 6% |
| B31-13 | Register allocation | 4% |
| B31-14 | Code emission | 3% |
| B31-15 | Linking | 8% |

Shares sum to 100%. Measurement: per-phase wall-ns and peak-bytes reported by `plkc build --profile-passes` into `pass-profile.json` (schema fixed in Volume 21 §21.5: `{kind, count, total_ns, peak_bytes}`, keys sorted). Linking includes the external linker invocation when the pipeline uses one; its cost is attributed wholly to B31-15. Termination and complexity bounds per phase are owned by the phase's volume (Volumes 11–17) and referenced here; a phase without a termination obligation is a G11 gap and fails the matrix check.

### 23.1.1 Phase attribution rules (exact)

Attribution law, binding for every timing claim:

1. Each phase's `total_ns` covers only that phase's own computation, including its allocations and the cache I/O it causes. Process startup and teardown are excluded from all phases and reported as `overhead_ns` in `pass-profile.json`.
2. Build-script execution (Volume 20 §20.3) is attributed to the build-script unit and to no phase of this table.
3. A cache-hit unit contributes 0 ns to phase totals; its cost was accounted when it was computed. Cache I/O (key computation, blob load and verification) is attributed to the phase that requests it.
4. The sum of phase totals plus `overhead_ns` must equal the build manifest's `total_wall_ms` within 1%; a larger drift is a measurement-harness defect (Severity 1), not a budget violation.
5. Parallel phases attribute each unit's time to its phase; idle worker time is reported as `idle_ns` and is excluded from phase totals but included in the efficiency computation of B31-34.

## 23.2 Memory usage (defines design.md 31.2, bullets B31-16..B31-25)

The memory budget contract: peak resident memory of the compiler for W1 must be ≤ 16 GiB at `-O0` and ≤ 32 GiB at `-O2` (measured as peak RSS via the harness of §23.8 Memory benchmarks). Component shares are ceilings on the peak (per-component peak RSS attributed by allocator hooks); exceeding a ceiling is a tracked warning with a review record; exceeding the total is a CI failure.

| Bullet | Component | Ceiling (share of peak) |
| --- | --- | --- |
| B31-16 | Peak compiler memory (total) | 100% (the ≤ 16 / ≤ 32 GiB bounds) |
| B31-17 | AST memory | ≤ 20% |
| B31-18 | Type system memory | ≤ 15% |
| B31-19 | Trait solver memory | ≤ 15% |
| B31-20 | Graph memory | ≤ 10% |
| B31-21 | Optimization analysis memory | ≤ 15% |
| B31-22 | Debug metadata memory | ≤ 10% |
| B31-23 | Incremental cache memory (in-memory query tables) | ≤ 10% |
| B31-24 | Parallel compilation memory overhead | ≤ 5% of the single-worker peak |
| B31-25 | Memory reclamation | ≥ 80% of peak RSS returned to the OS after build completion (measured at exit) |

Ceilings sum to 100% with the parallel overhead measured against the single-worker peak. Compiler memory safety itself is G12 (Volume 22 §22.0.1); this section bounds quantity, not correctness.

## 23.3 Incremental performance (defines design.md 31.3, bullets B31-26..B31-33)

All metrics are measured on the **touch-one-file workload**: W1 with one module edited (one function body changed, one type field added, one constant changed — three scenarios, all measured), then rebuilt incrementally per Volume 20 §20.5/§20.6.

| Bullet | Metric (exact definition) | Gate |
| --- | --- | --- |
| B31-26 | Rebuild minimization: fraction of unit-cache entries reused without recompilation | ≥ 90% in every scenario |
| B31-27 | Dependency precision: |true dependencies| / |recorded dependencies|, where true deps are computed by a full rebuild oracle | precision ≥ 0.95; recall = 1.0 exactly (a missed dependency is a correctness defect, OB-20-9) |
| B31-28 | Fine-grained invalidation: median size of the invalidated query set on a single-item edit, as a fraction of all queries | ≤ 5% |
| B31-29 | Cache hit rate: cache hits / cache lookups on the touch-one-file workload | ≥ 95% |
| B31-30 | Cache serialization overhead: (incremental build time) − (build time with cache reads but no writes), as a fraction of the non-incremental build time | ≤ 5% |
| B31-31 | Cross-module incremental optimization: units re-optimized after one module's interface digest changes, as a fraction of dependent units | ≤ 20% on W1 |
| B31-32 | Generic instance caching: instance-cache hit rate on the touch-one-file workload | ≥ 90% |
| B31-33 | Background analysis: p95 query latency of the LSP server for documents ≤ 2000 lines (Volume 21 §21.1 protocol) | ≤ 100 ms on the reference machine |

## 23.4 Parallel compilation (defines design.md 31.4, bullets B31-34..B31-43)

**Work assignment (G14, settled):** all parallel stages use fixed work assignment — the unit/function list is the canonical topological order (Volume 20 §20.3 Build ordering) and each worker takes the next unassigned item in that order; results are merged in canonical order, never completion order. Consequently, artifacts are byte-identical for worker counts J ∈ {1, 2, 4, 8} (OB-23-5; measured on W1 at `-O0` and `-O2`).

| Bullet | Definition |
| --- | --- |
| B31-34 | Module-level parallelism: units are the parallel tasks; parallel efficiency = T1/(J·TJ) ≥ 0.6 at J = 8 on W1 `-O0` (linking excluded) |
| B31-35 | Function-level parallelism: per-function tasks within a unit; enabled by default for the phases of B31-11..B31-14; deterministic merge per the work-assignment rule |
| B31-36 | IR optimization parallelism: pass execution per function in parallel; the pass sequence per function is the fixed pipeline order (Volumes 13/14); no cross-function pass reordering |
| B31-37 | Generic specialization parallelism: the instance queue is processed by all workers; instance outputs are content-keyed (Volume 20 §20.6), so assignment order cannot affect results |
| B31-38 | Backend parallelism: instruction selection, scheduling, and encoding per function in parallel under the same rule |
| B31-39 | Parallel code emission: object sections are emitted per function in parallel and concatenated in canonical function order; symbol tables are assembled in canonical order (G14) |
| B31-40 | Shared compiler state: shared state = immutable interned tables plus per-worker arenas; cross-worker writes occur only at recorded merge points with per-record atomicity (Volume 20 §20.3 Parallel builds) |
| B31-41 | Deterministic parallel execution: the byte-identity property above, including diagnostics emitted in canonical order (OB-23-5) |
| B31-42 | Synchronization costs: total synchronization time measured via counters and reported per phase as `sync_ns` in `pass-profile.json`; sync share of a phase must be ≤ 10% at J = 8 (tracked warning above) |
| B31-43 | Memory scaling: peak(J) ≤ peak(1) × (1 + 0.15 × (J − 1)) for J ≤ 8 (measured on W1) |

## 23.6 Optimization quality metrics (defines design.md 31.6, bullets B31-55..B31-66)

Every metric has an exact measurement definition; all are reported per §23.10 with median and MAD over ≥ 30 measured runs after 3 warmup runs, on the reference machine, with the configuration recorded. Counters come from the Volume 21 §21.5 closed counter set via `perf_event_open`; where the perf subsystem is unavailable the run is invalid, never approximated.

| Bullet | Metric | Exact definition |
| --- | --- | --- |
| B31-55 | Execution time | Wall-clock ns of the pinned workload run; median of ≥ 30 runs |
| B31-56 | Cycles per operation | (cycles counter) / (operation count from benchmark instrumentation); reported with 2 decimal places, integer math in per-mille internally |
| B31-57 | Instructions retired | `instructions` counter, median over runs |
| B31-58 | Branch misses | `branch-misses` counter, median; miss ratio = misses × 1000 / branches (per-mille, saturating) |
| B31-59 | Cache misses | `cache-misses` counter (LLC), median over runs |
| B31-60 | Memory bandwidth | Defined traffic proxy: (L1-dcache-loads + L1-dcache-stores) × 8 bytes, divided by elapsed seconds; the proxy convention is fixed and reported alongside the raw counters |
| B31-61 | Allocation count | Total allocator-hook events (allocations only) per run |
| B31-62 | Allocation bytes | Total bytes requested through allocator hooks per run |
| B31-63 | Stack usage | Maximum stack depth bytes from the stack-probe instrumentation (Volume 18 §25) |
| B31-64 | Code size | `.text` section bytes of the artifact (Volume 17 layout) |
| B31-65 | Startup time | Wall-ns from process start to the first application-defined output byte; median of ≥ 30 runs |
| B31-66 | SIMD utilization | Vector instructions / total instructions, counted over the artifact's hot-function set (top 10 functions by §21.5 CPU sampling of the pinned workload) via `plkc disasm` |

The benchmark workload set for these metrics is the pinned **quality set Q** of §23.6.1. Counters come from the Volume 21 §21.5 closed counter set via `perf_event_open`; where the perf subsystem is unavailable the run is invalid, never approximated.

## 23.7 Cost models (defines design.md 31.7, bullets B31-67..B31-76)

**Base models.** Two exact base models, referenced by every profitability model:

| Model | Definition |
| --- | --- |
| Dynamic instruction count (DIC) | Weights per instruction class: integer ALU 1; load 3; store 3; branch taken 2; branch not-taken 1; call/ret 4; integer divide 10; float ALU 4; vector ALU (128-bit op) 2; atomic RMW 20. Dynamic counts use the profile or, absent a profile, the static priors of the code-layout model (B31-74) |
| Static size | Bytes per instruction = encoding length from the Volume 15 instruction table, exactly |

**Microarchitectural terms (G10).** Every model takes target terms from the Volume 16 target cost tables: instruction latency, throughput, dependency-chain depth, branch-prediction priors, cache hierarchy (L1/L2/LLC sizes and latencies), memory bandwidth, SIMD width, register-file size, fusion pairs, load/store behavior, atomic cost. This satisfies the design.md directive: no model is based exclusively on abstract operation counts. Model weights are calibrated: the calibration obligation OB-23-10 re-fits the DIC weights against measured cycles on the calibration workload set (the quality workload set of §23.6) at every compiler minor release; a weight change without a new evidence artifact is invalid.

**The ten profitability models.** Decision rule form: apply the transformation iff modeled net benefit ≥ 0 under the stated formula; every rule is deterministic (ties broken as stated) and every constant is exact:

| Bullet | Model | Decision rule (exact) |
| --- | --- | --- |
| B31-67 | Inlining | Inline callee c into call site s iff est_calls(s) × 4 (saved call DIC) ≥ size_growth_bytes(c, s) × 100 / inline_threshold, with inline_threshold from the profile (Volume 20 §20.3) and est_calls from the call-graph static profile; recursion inlined only to depth ≤ 2 |
| B31-68 | Specialization | Specialize an instance iff the substitution makes ≥ 8 DIC of the callee body constant-foldable per call site (const-argument analysis) and the total instance count stays within the Volume 12 limit |
| B31-69 | Loop unrolling | Unroll iff body DIC ≤ 16 and static trip count ≥ 4; unroll factor = min(8, 256 / body_size_bytes); apply iff size growth ≤ 256 bytes |
| B31-70 | Vectorization | Vectorize iff the loop has no loop-carried memory dependence, ≥ 4 vectorizable scalar ops per iteration, and modeled speedup = scalar_DIC/vector_DIC ≥ 1.5 using target SIMD width |
| B31-71 | Allocation elimination | Eliminate iff the §22.3 B29-48 conditions hold (unobservable allocation); escape-analysis cost bounded to 4 pointer-dereference levels; modeled saving = 12 DIC per removed allocation (alloc + free) |
| B31-72 | Stack promotion | Promote to stack iff the address does not escape (provenance compute-only per SPEC-INDEX §3) and object size ≤ 8192 bytes; saving = 12 DIC plus allocator pressure relief |
| B31-73 | Representation selection | Choose the Volume 14 §21 representation minimizing (modeled DIC + 2 × size bytes)/1000; ties broken by smaller size, then lexicographically smallest representation id |
| B31-74 | Code layout | Order blocks to minimize expected taken-branches with static priors: loop back-edge taken with probability 0.9, forward branch taken 0.6, call-return fallthrough 0.8; with profile data, priors are replaced by measured frequencies |
| B31-75 | Instruction scheduling | List scheduling with target latency/throughput tables minimizing modeled cycles on the dependency DAG; ties broken by ascending instruction id (determinism, G14) |
| B31-76 | Register allocation | Spill priority = uses × 10^3 + loop_depth × 10^6 − size_cost, exact integer math in u64 with checked multiply, spills chosen in ascending benefit order until pressure ≤ available registers (SPEC-INDEX §5.8, restated binding here) |

Evidence levels per model (G6): Level 1 = this table (formal model); Level 2 = microarchitectural analysis recorded in the model's review record; Level 3 = empirical validation on the quality workload set per §23.10. All three levels are required before a model constant may change.

## 23.9 The optimization utility function U(T) (implements verification standards G7)

For every optimization candidate T, the prioritization record computes:

```
U(T) = B(T) · R(T) · F(T) / K(T)
```

with exact measurement definitions:

| Term | Exact definition | Unit |
| --- | --- | --- |
| B(T) | Benefit: (median_execution_time(P) − median_execution_time(T(P))) / median_execution_time(P) over the benefit set B20 of §23.6.1, measured per §23.10; clamped below at −1 | dimensionless fraction |
| R(T) | Reliability: the fraction of the 20 workloads of B20 where the measured improvement ≥ 0.01 (1%) | dimensionless, [0, 1] |
| F(T) | Frequency: applicable opportunities per KLOC on W1, counted from the pass's remark stream (Volume 21 §21.5) | opportunities / KLOC |
| K(T) | Cost: K_impl + K_proof + K_compile + K_maint, where K_impl and K_proof are engineering-week estimates recorded in the dossier review, K_compile = (compile-time overhead fraction on W1) × 10, K_maint = estimated maintenance weeks per year | dimensionless cost units |

Decision law: candidates are ranked by U descending; a transformation enters the default pipeline iff U ≥ 1.0 and the Volume 22 §22.3 gate passes. U is a prioritization heuristic, not a mathematical law (verification standards G7); its inputs B and F must be measured, and the K components must be recorded in a review artifact. The dossier of every accepted pass records its U computation with artifact paths (OB-23-12).

## 23.10 Measurement protocol (implements standards.md §13)

Every performance claim (budget, metric, cost-model calibration, U(T) input) requires one evidence artifact in `bench/evidence/<id>.json` (canonical JSON) with exactly these fields, per CEP&CC §13.1:

| Field | Content |
| --- | --- |
| `source_revision` | git commit id of the measured tree |
| `compiler_version` | version string + toolchain fingerprint (Volume 20 §20.4) |
| `compiler_flags` | the canonical config flag list (Volume 20 §20.4 Compiler configuration capture) |
| `target_cpu` | CPU model string of the reference machine |
| `frequency_state` | governor state: `pinned-performance` or `unavailable` (turbo status recorded) |
| `input_dataset` | dataset name + BLAKE3-256 digest |
| `harness_version` | benchmark harness version string |
| `metrics` | the measured values per §23.6/§23.1 definitions (median, MAD, CI) |
| `disassembly_hash` | BLAKE3-256 of the `plkc disasm` output over the hot-function set (generated-code claims only) |
| `environment` | per standards.md §13.2: thread pinning, turbo, CPU isolation, background work, huge pages, warm/cold caches — each `enabled` or `unavailable` |

Protocol law: (M1) steady-state measurements warm caches (3 warmup runs); cold measurements flush and say so. (M2) every hot compiler function's `CEP:COST` comment references an evidence artifact id (CEP&CC §13.3 cost categories: best, expected, worst, cache-miss, mispredict, fault cases stated where applicable). (M3) regression gates of §23.5/§23.8 run in CI and cannot be waived except by a review record with an expiry date. (M4) measurements without a complete evidence artifact are invalid and must not be cited in any volume or review. Evidence ids have the form `ev-<kind>-<seq>` where kind ∈ {`budget`, `quality`, `calibration`, `utility`} and `<seq>` is a monotonically increasing integer; the mapping id → artifact file is recorded in `bench/evidence/index.json`.
